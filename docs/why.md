# Why mem-engine

## The problem

A coding agent forgets everything between sessions. Every new session starts by re-reading files, re-asking what was decided and re-discovering the same pitfalls. Long-term memory fixes that, but every memory system pays for itself in tokens, and the existing options pay too much or give up the parts that make memory useful.

mem-engine tries to solve four concrete problems.

### 1. Memory that costs more than it saves

Claude Code's native auto-memory loads the whole `MEMORY.md` index at the start of every session: the first 200 lines or 25 KB, before the first question. With a few hundred memories per project that is 12 to 18 KB of context in every session, whether the task needs it or not.

Memory systems that summarize every observation with an LLM have the opposite problem: they spend tokens on every tool call to write the memory, then inject a large summary when the session opens.

mem-engine opens a session with a handoff of at most 1,200 characters (about 300 tokens) and lets the agent pull the rest on demand, in two or three cheap calls. Capture never calls an LLM.

### 2. Memory you cannot see or fix

When memory lives only in a database or in summaries generated by a model, wrong memories stay wrong. mem-engine keeps curated memory as plain Markdown files in a git repository per project, so every change has a history, and ships a local web viewer to browse, search, edit and delete what was recorded.

### 3. Memory that leaks between projects

A memory recorded while working on one project must not show up in another. This matters most for consultants and contractors working for several clients, where cross-client leakage is a contractual problem, not a nuisance. mem-engine scopes every search to the current project plus a personal `user` scope, and lets you group repositories by path prefix (for example, one group per client) so the isolation boundary is the one you choose.

### 4. Capture that fails silently

A hook that crashes, times out or cannot reach the database usually loses the event without telling anyone. mem-engine never runs a resident service that can be down; every hook is the same binary writing straight to SQLite, events that cannot be written go to a spool that the next process drains, and failures are counted and shown by `mem doctor` and the viewer.

## Prior art

mem-engine is a synthesis of two projects, keeping what worked in each and dropping what did not.

### claude-mem

[thedotmack/claude-mem](https://github.com/thedotmack/claude-mem) is a Claude Code plugin that records tool usage, compresses it into semantic summaries with an LLM and stores them in SQLite with vector search, served by a local worker.

Kept from it:

- **Layered search over MCP:** a short list first (`search`), the surrounding events next (`timeline`), full content only for the ids that matter (`get`). This is what keeps lookups cheap.
- **A local web viewer** with a live feed of what is being captured.

Left out:

- An LLM call per observation, and a large context injection when the session opens. This is where the token cost came from.
- A resident worker process. When it is down, capture is lost without warning, and it is one more service to install and monitor.

### ai-memory

[akitaonrails/ai-memory](https://github.com/akitaonrails/ai-memory) is a long-term memory system for coding agents built on a plain-Markdown wiki kept in git, with capture that does not depend on an LLM and a short handoff between sessions and between agent CLIs.

Kept from it:

- **Capture without an LLM** and **a short handoff** instead of a full index.
- **Curated memory as Markdown in git**, the source of truth, with the database only as a rebuildable index.

Missing for this use case, and added here:

- The layered search and the web viewer from claude-mem.
- Isolation by project and by path-prefix group.

## Goals and non-goals

Success means the session opens with at most a few hundred tokens of memory, the agent finds what it needs in two or three cheap calls, and the user can see and correct the memory in a browser.

It is a failure, even if it technically works, when:

- opening a session costs more tokens than the `MEMORY.md` it replaces;
- a hook fails without leaving a trace;
- a slow hook blocks the agent's turn;
- data from one project shows up in a search from another without an explicit request;
- captured content is sent to any external service.

Out of scope for now: LLM summaries per observation, a dedicated vector database, agents other than Claude Code (the MCP side is already agent-neutral) and sync between machines.

`mem bench` measures the first point on your own memory; see [Benchmark](../README.md#benchmark).
